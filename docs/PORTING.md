# Как устроен перенос на Android

## Как работает без root

В Windows-версии `winws` и в Linux-версии `nfqws2` перехватывают готовые пакеты (WinDivert, NFQUEUE) и отправляют свои через raw-сокеты. Без root приложению это недоступно, поэтому схема другая:

```text
приложения -> VPN-интерфейс -> hev-socks5-tunnel -> ciadpi (ByeDPI) -> сайт
```

`hev-socks5-tunnel` превращает пакеты из VPN-интерфейса в соединения SOCKS5. `ciadpi` открывает обычные сокеты к сайтам и влияет на трафик тем, что доступно обычному приложению: границами записи, TTL и порядком передачи. Само приложение исключено из VPN через `addDisallowedApplication`, иначе соединения `ciadpi` снова попадали бы в VPN.

Конфиги `.vpn` генерирует [tools/bat2vpn.py](../tools/bat2vpn.py). Каждая строка файла задаёт группу `ciadpi`, побеждает первая подходящая.

## Что становится чем в режиме VPN

| Windows (winws) | VPN (ciadpi) | Что меняется |
| :--- | :--- | :--- |
| `fake` для QUIC, Discord, STUN | `-a N -l файл -t 64` | Тот же фейк с тем же числом повторов и обычным TTL. `ciadpi` не смотрит внутрь UDP, поэтому хостлист не применяется: фейк идёт перед первым пакетом любого потока на этих портах |
| `fake,multisplit`, `fake,fakedsplit` | `-s P -f -1 -O P -l файл -t 8` | Первый кусок настоящий, дальше фейк с той же позиции. Для DPI вместе они выглядят как целый ClientHello с чужим SNI |
| `multisplit` с `seqovl` и шаблоном | `-s P -f -1 -O P -l шаблон -t 8` | Перекрытие seq сделать нельзя, поэтому шаблон показывается как фейк |
| `fake,multidisorder` | `-f -1 -l файл -t 8` | Настоящие данные ядро передаёт повторно одним куском, изменить их порядок после фейка нельзя |
| `multidisorder` без фейка | `-d P` | TTL=1 у первой части, ядро передаёт её заново |
| `hostfakesplit` | `-s 0+h -f 0+he -O 0+h -Q orig -n хост -t 8` | Настоящий ClientHello с поддельным именем. `altorder=1` повторить нельзя, поэтому порядок один |
| `syndata` | ничего | Нужен raw-сокет |
| `ts`, `badseq`, `md5sig` | `-t 8` | Подделать заголовок нельзя, вместо этого малый TTL. `--md5sig` не используется: на части ядер Android он ломает соединение |
| `--dpi-desync-repeats` для TCP | `--fake-hold 350` | Фейк держится на месте настоящих данных, и ядро повторяет его само |
| несколько `--dpi-desync-fake-tls` | один фейк | Выбирается настоящий ClientHello, а не служебные `0x00000000` и `stun` |
| `--fake-tls-mod=rnd`, `sni=X` | `-Q rand`, `-n X` | `dupsid` нет |
| `midsld`, `sniext+1` | `0+hm`, `-4+h` | Середина имени вместо середины домена 2 уровня |
| `--hostlist-exclude` | группа без действий перед первой группой с хостлистом | |

Профили с `--ipset` переносятся с адресом-заполнителем `%IPSET%`: приложение подставляет список в выбранном режиме (см. «Перенос service.bat»). Для `-K u` хостлист не проверить, поэтому профиль UDP с ipset пропускается, если те же порты уже взяла группа с хостлистом. Профили фильтра игр (`%GameFilter%`) не переносятся: в Windows они нужны для игр через Steam.

Первой идёт группа без действий с `vpn-ipset-exclude.txt`: локальные сети и адреса из `ipset-exclude.txt` не трогает ни один профиль Windows-версии.

После перевода различаются 18 конфигов из 22. Одинаковыми получаются ALT и ALT4, ALT2 и ALT7, а также FAKE TLS AUTO ALT, ALT2 и ALT3.

## TTL фейков

Фейк с TTL 8 должен дойти до оборудования провайдера и не дойти до сайта. Если сервер ближе 8 прыжков, например кэш Google у самого провайдера, фейк дойдёт до него и соединение сломается. `ciadpi` не умеет подбирать это значение для каждого соединения, как `autottl` в `nfqws2`, поэтому его подбирает проверка конфигов: если лучшие конфиги открыли не все сайты, она пробует TTL 4, 6, 10 и 12 и запоминает значение для конфига. В списке есть и конфиги без фейков для TCP: ALT5, `vpn disorder`, `vpn split`, `vpn tlsrec` и `vpn oob`.

После замеров на настоящей сети видно, что TTL 8 часто оказывается слишком большим. На проверенном Wi-Fi окно от 3 до 6: с TTL 2 фейк не доходит до DPI, а с 7 и выше доходит до близких серверов Google и ломает `www.gstatic.com` и `fonts.googleapis.com`, без которых не работает поиск. Поэтому в `vpn combo` TTL меньше, а TTL в «Подобрать» подбирается отдельно для Wi-Fi и мобильной сети.

## Локальный DNS

Приложения спрашивают адрес `198.18.0.2`. По нему ничего не слушает: `ciadpi` с опцией `--dns-port` ([native/patches/byedpi-dns-port.patch](../native/patches/byedpi-dns-port.patch)) отправляет весь UDP на порт 53 в [DnsForwarder](../app/src/main/java/org/zapretcap/app/DnsForwarder.java) на `127.0.0.1`, а ответ возвращает от имени исходного адреса. Публичный адрес вместо `198.18.0.2` не подходит: Chrome, увидев `1.1.1.1`, сам уходит на свой DoH.

Измерения на настоящих сетях, из-за которых он появился:

- На Wi-Fi UDP-запрос `www.youtube.com` к `1.1.1.1`, `8.8.8.8` и `195.208.4.1` получает ответ NXDOMAIN с флагом AA: подделка по дороге. Настоящий ответ дают DoH и DNS Яндекса.
- В режиме белых списков у оператора `1.1.1.1` и `8.8.8.8` не отвечают, а `77.88.8.8` отвечает. С DNS, заданным жёстко, через VPN не открывался ни один из 29 сайтов, хотя разрешённые сайты по адресу работали.

Порядок: DoH Cloudflare и Google, затем с шагом 250 мс UDP Яндекса, UDP публичных серверов, DNS сети. Побеждает первый ответ с адресами, а пустой ответ и NXDOMAIN ждут ещё 700 мс: их подделывают. Сервер, ответивший адресами, запоминается и спрашивается первым, поэтому в белом списке запрос не ждёт недоступный DoH. Первый запрос долгий из-за загрузки TLS, поэтому прогрев идёт до поднятия туннеля. Если совсем никто не ответил, отдаётся устаревший ответ из кэша.

## Смена сети

Приложение исключено из VPN, но система присылает ему события и про сам туннель. Им нельзя верить на слово: туннель принимался бы за новую сеть. Поэтому событие только будит проверку, а настоящую сеть определяет [NetKind.physical](../app/src/main/java/org/zapretcap/app/NetKind.java). Если сеть правда сменилась, движок перезапускается с конфигом этой сети: соединения приложений сразу обрываются, и те подключаются заново. IPv6 заводится в туннель, только если он есть в настоящей сети, иначе приложения ждут отказа по каждому адресу IPv6. Если движок завис или упал, он запускается заново, и только после трёх быстрых сбоев подряд обход выключается с ошибкой.

## Подбор конфига

Кнопка **Подобрать** ([ConfigTester.java](../app/src/main/java/org/zapretcap/app/ConfigTester.java)) заменяет тест конфигураций из `service.bat`. Для каждого конфига запускается отдельный `ciadpi`, и через него открываются сайты из `utils/targets.txt` Windows-версии, кроме проверок ping. Само приложение исключено из VPN, поэтому проверка не требует разрешения на VPN и не мешает работающему обходу.

Отличия от теста Windows-версии:

- **Застывание.** Сайт считается открытым, только если ответ HTTP читается до конца или до 64 КБ. DPI часто пропускает рукопожатие и останавливает соединение после 16-20 КБ.
- **DNS.** Адреса берутся через тот же локальный DNS, что и у приложений. Заглушка в DNS провайдера закрыла бы сайт при любом конфиге.
- **Побочный вред.** Кроме заблокированных сайтов проверяются поисковики и их ресурсы: конфиг, который ломает их, проигрывает. Проверяются и добавленные домены.
- **Устойчивость.** Пять лучших конфигов проверяются ещё дважды, в счёт идёт худший результат.
- **Совпадающие конфиги** проверяются один раз.
- **TLS** проверяется в той версии, которую выберет система, а не отдельно 1.2 и 1.3.

## Правки сторонних исходников

**byedpi.** С `--fake-offset` функция `munmap` получала невыровненный адрес и не освобождала память, по несколько килобайт на соединение. Исправление: [native/patches/byedpi-fake-offset-munmap.patch](../native/patches/byedpi-fake-offset-munmap.patch).

**byedpi, фильтры групп** ([native/patches/byedpi-filters.patch](../native/patches/byedpi-filters.patch)). Диапазон портов `-V` сравнивался в сетевом порядке байтов, поэтому `-V 50000-50100` (Discord) совпадал с половиной всех портов, например с 5000 и 51820. А адрес UDP хранится как `::ffff:a.b.c.d`, и проверка ipset видела в нём совпадение с `0.0.0.0/8`. Теперь порты сравниваются после `ntohs`, а такой адрес проверяется как IPv4.

**byedpi, `--fake-hold`** ([native/patches/byedpi-fake-hold.patch](../native/patches/byedpi-fake-hold.patch)). Фейк в `ciadpi` уходит один раз: данные фейка кладутся на место настоящих, а настоящие ядро отправляет позже повтором. С `--fake-hold N` движок ждёт N мс, прежде чем вернуть настоящие данные, и за это время ядро само повторяет фейк. Это замена `--dpi-desync-repeats` из Windows-версии. На сервере видео YouTube по Wi-Fi один фейк прошёл в 37 попытках из 48, с удержанием 350 мс в 48 из 48. Цена: первое соединение с сайтом из списка открывается на 0,35 с дольше. Без удержания каждое четвёртое-пятое соединение к серверу видео замерзало на 30 секунд, отсюда долгий старт видео.

**byedpi, `--dns-port`.** Перенаправляет UDP на порт 53 в локальный DNS: [native/patches/byedpi-dns-port.patch](../native/patches/byedpi-dns-port.patch).

**libnetfilter_queue.** Патч автора zapret2 для сборки под Android: [native/patches/libnetfilter_queue-android.patch](../native/patches/libnetfilter_queue-android.patch).

В `native/third_party` все патчи уже применены.

## Особенности Android

**Запуск движка.** С Android 10 программы можно запускать только из папки нативных библиотек приложения. Поэтому `ciadpi` лежит в APK как `libciadpi.so`, а в `build.gradle` включён `useLegacyPackaging`.

**Режима root больше нет.** Раньше был второй режим с настоящим `nfqws2` и правилами iptables. Он убран: обходу хватает VPN, а root есть на немногих телефонах. Исходники `nfqws2` и его библиотек остались в `native/`, но не собираются.

## Прокси Telegram

[tg-ws-proxy](https://github.com/Flowseal/tg-ws-proxy) написан на Python. Здесь его логика перенесена на Java, чтобы не везти в APK среду Python. Пакет `org.zapretcap.tgproxy` не зависит от Android, поэтому его можно запускать и проверять на компьютере.

**Маршруты те же, что в исходном проекте, и в том же порядке.** Сначала WebSocket через правила DC → IP, затем Cloudflare Worker и CF-прокси, в конце прямой TCP. Медиа через CF-прокси сначала пробуют HTTP/2, повторы пакетов при обрывах работают так же.

**Потоки вместо asyncio.** Каждому соединению соответствуют обычные блокирующие потоки. В Python всё состояние каналов HTTP/2 защищал единственный поток событий, здесь его защищает один монитор на линию. Сеть и ожидание других потоков всегда находятся вне монитора.

**HTTP/2 через OkHttp.** Повторы в нём выключены: повторный POST отправил бы пакет Telegram дважды.

**Отличия от исходного проекта.**

- Прокси не зависит от основного обхода. Приложение исключено из собственного VPN, поэтому соединения прокси идут напрямую. Если в его настройках выбран конфиг, [TgEngine](../app/src/main/java/org/zapretcap/app/TgEngine.java) запускает для прокси отдельный `ciadpi`, и соединения идут через него по SOCKS5. Раньше прокси ходил через движок основного обхода, и конфиг, хороший для YouTube, мог сломать Telegram. Совет исходного проекта добавить домены Cloudflare в списки zapret выполняется сам: `Data.applyLists` дописывает их в список. В исходниках эти имена хранятся только в закодированном виде, как и в tg-ws-proxy.
- Приём обхода может сломать рукопожатие: фейк с чужим именем доходит до сервера, если тот ближе его TTL. Поэтому соединение, не установленное через движок за 5 секунд, повторяется напрямую. Без этого любой конфиг с фейками мог отключить датацентры 1, 3 и 5. В режиме root такого повтора нет: `nfqws2` обрабатывает пакеты на уровне ядра.

**Запас соединений рассчитан на телефон.** В исходном проекте он рассчитан на компьютер с постоянной связью и всегда полон. Измерения на настоящих серверах показали: Telegram закрывает простаивающий WebSocket ровно через 60 секунд, а на ping, pong и пустой кадр отвечает закрытием, поэтому проверить соединение перед выдачей нельзя. Отсюда такие решения:

- Запас держится только три минуты после последнего подключения клиента. Постоянный запас из 16 соединений открывал бы их заново каждую минуту, не давая модему уснуть.
- Соединение живёт в запасе не больше 50 секунд, и первым отдаётся самое свежее.
- Если запас пуст, клиент до 3 секунд ждёт новое соединение и только потом уходит на запасной маршрут: подключение через Cloudflare не быстрее.
- NAT оператора, DPI или сон телефона могут убить соединение молча, и сокет этого не заметит. Если соединение старше 10 секунд не получило ответа за 4 секунды, сессия закрывается, весь запас этого датацентра выбрасывается, и клиент сразу подключается заново. Так одна неудача заменяет круг по всем мёртвым соединениям.
- Если соединение устанавливается, но ответа нет дважды подряд, значит, DPI режет данные после рукопожатия. Маршрут WebSocket отключается на минуту, а при повторах до 10 минут. Домен Cloudflare, через который не было ответа, забывается.
- При смене сети ([TelegramProxyService](../app/src/main/java/org/zapretcap/app/TelegramProxyService.java)) все соединения закрываются сразу, а не ждут таймаута.

**Что ещё добавлено для телефона.** Адреса перебираются с IPv4: неисправный IPv6 на мобильной сети съедал бы весь таймаут. Линии HTTP/2 проверяются ping каждые 15 секунд. Необработанное исключение в потоке прокси только записывается в журнал: на Android оно завершило бы весь процесс вместе с VPN. Если приложение всё же упало, причина сохраняется и видна в журнале.

**Что не перенесено.** Fake TLS и PROXY protocol нужны, когда прокси стоит на отдельном сервере за nginx, а здесь он слушает только `127.0.0.1`. Автообновление не нужно: APK обновляется вручную. Тестовые датацентры есть в ядре, но не вынесены в настройки.

## Как это проверено

**Эмулятор Android 15, x86_64.** Запуск приложения, разрешение на VPN, смена конфига на лету, выключение, падение движка. Пакеты на выходе из устройства смотрит [tests/sniff.c](../tests/sniff.c), он требует `adb root`. Там же скрипт root-режима запускался из `adb shell`, и порядок пакетов совпал с Linux-версией.

**Изолированная сеть на Linux.** [tests/vpn-sandbox-test.sh](../tests/vpn-sandbox-test.sh) запускает все конфиги VPN через настоящий `ciadpi`. Эмулятор для этого не подходит: его сеть не учитывает TTL, и фейк доходит до сайта. В тесте сервер сам отбрасывает пакеты с малым TTL, поэтому видно, восстанавливается ли соединение после фейка.

**Прокси Telegram.** [tests/tgproxy-test.sh](../tests/tgproxy-test.sh) запускает проверки ядра на компьютере, в том числе разбор протокола и повторы HTTP/2 на поддельном транспорте. [tests/mtproto_probe.py](../tests/mtproto_probe.py) отправляет через прокси настоящий запрос `req_pq_multi` и ждёт ответ `resPQ` от настоящего датацентра. Так проверены: собранный APK в эмуляторе на маршрутах WebSocket, CF-прокси и HTTP/2, с VPN и без него, при смене конфига на лету, после перезагрузки и с занятым портом, а на компьютере прямой TCP, отказ при неверном ключе и отказ при чужом сертификате.

[tests/mtproto_soak.py](../tests/mtproto_soak.py) держит соединения открытыми и отправляет запросы раз в 15-20 секунд: 5 минут через APK и 3 минуты через APK с VPN без единого обрыва, а эталонный tg-ws-proxy ведёт себя так же. В эмуляторе проверены молча умершие соединения (правила iptables для их портов), обрезание данных после рукопожатия и смена сети. До изменений в первом случае клиент получал 4 мёртвых соединения подряд, после них одну неудачу за 4 секунды.

**Подбор конфига** проверен в эмуляторе с упрощённым DPI: правило iptables сбрасывает пакет с именем сайта, поэтому конфиг с разбиением проходит, а без него нет. В эмуляторе фейки доходят до сервера, поэтому настоящий порядок конфигов и пользу от другого TTL там не проверить. Новые конфиги проходят [tests/vpn-sandbox-test.sh](../tests/vpn-sandbox-test.sh).

**Что не проверено в прокси Telegram:** настоящий клиент Telegram с рабочей сессией, а значит, и повтор пакетов на настоящем трафике, Cloudflare Worker с настоящим доменом (проверен только отказ при несуществующем).

**Настоящий телефон.** [tests/phone/](../tests/phone/): Redmi Note 13, Android 14, Wi-Fi домашнего провайдера и LTE в режиме белых списков. `phone-matrix.sh` проверяет приёмы движка напрямую, `phone-vpn.sh` идёт через настоящий VPN, `phone-white.sh` сравнивает TCP, UDP и DNS, `phone-switch.sh` меняет сеть под нагрузкой. Рядом с проверками идёт контроль без обхода: попытка не считается, если не прошёл и он, тогда виновата сеть.

**Что так проверить нельзя:** результат на другом провайдере может отличаться.

## Сравнение с Windows- и Linux-версиями

Windows-версия ([zapret-discord-youtube](https://github.com/Flowseal/zapret-discord-youtube)) запускает `winws` с 22 стратегиями. Linux-версия (Zapret Cap для Linux) переводит те же стратегии на `nfqws2` скриптом `tools/bat2conf.py`. Оба движка работают с пакетами напрямую, приложение без root нет.

| Приём | Windows и Linux | Приложение |
| :--- | :--- | :--- |
| Фейк QUIC, Discord, STUN | фейк с повторами, только для доменов из списка | фейк с теми же повторами для любого адреса на этих портах: без root внутрь UDP не заглянуть |
| `multisplit`, `fakedsplit` | разбиение и фейк с поддельным заголовком | разбиение и фейк с малым TTL |
| `seqovl` с шаблоном | перекрытие номеров сегментов | шаблон отправляется как фейк с малым TTL |
| `fooling=ts`, `badseq`, `md5sig` | фейк, который сервер отбросит по заголовку | фейк с малым TTL: до DPI доходит, до сервера нет |
| `syndata` | данные в SYN | нет, нужен raw-сокет |
| `repeats` у фейков TCP | до 11 копий | повторы ядра за время `--fake-hold`, обычно 2–3 копии |
| `ip-id=zero` | есть | нет |
| `hostfakesplit` с `altorder` | есть | один порядок |
| хостлисты, исключения | есть | есть, их можно править в приложении |
| ipset с режимами | есть | есть |
| фильтр игр | есть | нет, не нужен на телефоне |
| замена активных фейков | есть | только фейк Discord |
| hosts | запись в системный файл | ответ локального DNS |
| проверка конфигов | `service.bat`, `zapret test` | **Подобрать**, отдельно для Wi-Fi и мобильной сети |
| DNS | системный, рекомендуют включить DoH в браузере | свой: DoH и запасные серверы для всего телефона |

Главное следствие: подделать заголовок пакета без root нельзя, поэтому все фейки здесь держатся на малом TTL. Он должен быть больше расстояния до DPI и меньше расстояния до сайта. Поэтому TTL здесь подбирается под сеть, а конфиг выбирается отдельно для Wi-Fi и мобильной.
